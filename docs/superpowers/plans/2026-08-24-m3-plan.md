# M3 实现计划:智能与转码(2026-08-24)

PRD 依据:§5.5(本地 AI 选片)、§5.6(转码引擎)、§5.8(成片命名校验)、§7(验收:
千张连拍聚类+评分 ≤5 分钟;Log 素材批量转代理入「4. 转码素材」)。
另含 M2 收敛文档记入的 **M3 前置批**(架构债)。

## 设计主轴:统一后台作业子系统(JobManager)

M2 的教训:交付打包同步阻塞、索引线程各自为政、互斥靠命令层散装接线。
M3 的三大件(转码、AI 分析、迁移后的交付)都是「长任务 + 进度 + 取消」形态——
先建一个共享的 JobManager,三者共用,交付顺势迁移,前置批的大头自然消化。

- `core/jobs.rs`:JobId、JobKind(delivery/transcode/analyze)、JobState
  (queued/running/paused/done/failed/cancelled)、进度(done/total/bytes/message)、
  取消令牌(AtomicBool,作业在安全点检查)、并发上限(转码 1、分析 1、交付 1,
  互不阻塞但同 kind 排队)。
- 事件 `job://progress`(≥500ms 节流 + 终态必发),前端统一 JobsPanel。
- 与 OpsMutex 集成:delivery/transcode 作业在 begin 时拿对应 guard,
  guard 存进作业结构,Drop 自动释放(panic 安全沿用)。
- 作业不持久化(重启即消,幂等重跑安全——转码/交付都是零覆盖语义);
  杀进程后半成品用既有 staging 后缀清理。

## 任务分解

### T0 前置批(先行,独立提交)
- **T0.1 交付迁移 JobManager**:build_delivery 变异步作业(进度=文件粒度,
  取消在文件边界),前端确认屏改为进度视图;OpsMutex 语义不变。
- **T0.2 ProjectStats 缓存**:AppState 内 (nas_root, mtime 指纹)→scan 结果缓存,
  变更命令后失效;命令层不再每次全 NAS 扫描。
- **T0.3 缩略图懒取**:自定义 `thumb://` 协议(tauri register_uri_scheme_protocol)
  按需读缓存文件,替换 base64 内联;失败回占位。IPC 体积从 ~5MB/页降到 KB 级。
- **T0.4 回收站索引压缩**:`list_trash` 折叠后,若「墓碑数 > 存活行数 × 4 且总行 > 500」
  在 empty_trash 末尾做一次安全压缩:写唯一临时文件+原子替换,**压缩前后都要求
  持有 OpsMutex 交付/分类空闲窗口**,并发追加窗口语义同 M2 声明(行丢失=实体可见孤儿)。
- **T0.5 命令层集成测试基建**:tauri::test::mock_app 驱动 invoke_handler,
  至少覆盖互斥闸接线(打包中 trash 拒)与一条 sorting 命令全链路。
- 顺延不做(记录):跨机分类事件重放(依赖日志镜像设计,M4/后续)、
  file_type Err 注入测试(不可注入,维持声明)。

### T1 转码引擎(§5.6,工况 A)
- **T1.1 ffmpeg sidecar 分发**:三平台静态 ffmpeg/ffprobe 捆绑为 tauri sidecar
  (externalBin);启动探测版本;缺失→设置页可见 error(零静默),转码功能禁用态。
- **T1.2 硬编探测**:`ffmpeg -encoders` + 各平台探针(启动一次,缓存):
  h264/hevc 的 NVENC/QSV/AMF/VideoToolbox/VAAPI,全无→libx264/libx265。
  探测结果进设置页「能力」区展示。
- **T1.3 代理转码作业**:选中「2. 原始素材」下相机夹(或整项目)→ 逐文件
  ffprobe 判定(编码/码率/色彩空间,Log 判定按元数据启发 + 高码率阈值)→
  转 1080p H.264 代理(码率档固定)到 `4. 转码素材/<相机夹>/`,零覆盖
  (staging `.transpart` + rename_no_replace),失败逐文件上报;进度按输出时长解析
  ffmpeg -progress。
- **T1.4 归档转码**:HEVC 10-bit 三档(高质量 CRF18/平衡 CRF23/高压缩 CRF28,
  硬编时映射对应码率档);输出到用户选择目录;默认不动原件。
- **T1.5 拷完自动转代理**:StartCopyInput 加 `auto_proxy` 选项(工况 A 显示),
  拷卡任务 done 时投递转码作业(NAS 端源)。
- UI:CopyTask 屏勾选项;新「转码」屏(工况 A):任务队列、档位选择、进度、失败列表。

### T2 AI 选片基建 + 客观质量分(§5.5)
- **T2.1 ort 集成**:`ort` crate(CPU EP 基线;macOS 上 CoreML EP、Windows 上
  DirectML EP 作为 feature 尝试,失败静默回 CPU——**回退要发 info 通知**,零静默)。
  模型文件随应用 resources 分发,启动校验 xxh3。
- **T2.2 纯算法评分**(不依赖模型,先行落地):清晰度=灰度拉普拉斯方差;
  曝光=直方图过曝/欠曝比例。对「待分类」在索引线程内顺带计算(降采样后算,
  复用已解码缩略图,避免二次解码)。
- **T2.3 人脸+闭眼**:YuNet(ONNX,~230KB)检测人脸与 5 关键点;闭眼判定用
  眼部裁块 + 轻量开闭眼分类模型(MobileNet 裁剪版);小于最小像素的脸不判
  (PRD 诚实边界)。输出 faces[{bbox, eyesClosed?}]。
- **T2.4 embedding + 连拍聚类**:MobileNet 级 embedding(输入 224²,输出 512d)
  + 规则:拍摄时间差 ≤3s 且余弦相似度 ≥阈值 → 同组;组内按综合分排序,
  首位标「建议保留」。groupId 契约(M2 预留的字段)接通。
- **T2.5 荐优与 UI**:综合分 = 清晰度/曝光/闭眼惩罚加权;网格角标(分数区间/
  闭眼/糊片标记)、连拍组折叠(展开查看全组)、「按建议筛选」;
  **AI 只标注不动文件**,采纳=用户自己按既有分类操作执行。
- **T2.6 性能验收**:千张 JPEG(含连拍)聚类+评分 ≤5 分钟(CI 无 GPU,以 CPU 基线
  测;用生成的合成图集做基准测试,cargo bench 或带计时的集成测试)。
- 分析结果持久化:`.ocard/analysis/<xxh3(rel+size+mtime)>.json`(NAS 共享,多机复用),
  损坏行跳过计数上报(沿用零静默模式)。

### T3 成片命名校验(§5.8,轻量)
- `core/naming.rs` 扩展:解析 `时间日期_片名_分辨率_用途_版本`,识别 720p 预览/4K 成品。
- 命令 `check_final_cuts(project_id)`:扫描「6. 成片」,返回逐文件判定;
  工况 A 项目详情页显示校验列表(黄标不合规 + 原因);不做常驻 watch
  (进入页面时扫描 + 手动刷新,轻量原则)。

### T4 测试与收口
- Rust:jobs 状态机、ffmpeg 参数构造(不真转码)、探测解析、评分算法
  (合成图:清晰 vs 高斯糊、过曝/欠曝)、聚类规则、命名解析矩阵、
  真 ffmpeg 冒烟(CI 装 ffmpeg 跑 1 秒合成视频转码)、ONNX 推理冒烟(模型随 repo?
  模型体积>50MB 则 CI 缓存下载 + 校验)。
- 前端:JobsPanel、转码屏、角标/组折叠、命名校验列表,全部含错误态,变异验证。
- E2E:转码流(合成视频→代理落盘断言)、命名校验冒烟。
- 评审:实现评审 opus + gpt-5.6-sol(max)并行 → 修复波 → 终审 gpt-5.6-sol(max)
  + fable-5 双票(沿 M2 流程)。

## 关键决策(计划评审请重点裁)
1. ffmpeg **捆绑**(三平台 sidecar,包体 +60~90MB)vs 首用下载(需校验与离线处理)。
   倾向捆绑:内网环境,离线可用性优先。
2. ONNX 模型选型与来源:YuNet(Apache-2.0)+ MobileNetV3-embedding + 开闭眼小模型;
   模型总体积控制 <30MB,随包分发。若找不到许可证干净的开闭眼模型,
   降级为「眼部关键点纵横比」启发式并如实声明精度边界。
3. 分析结果放 NAS(`.ocard/analysis/`)共享 vs 本机缓存:倾向 NAS(多机复用,
  与缩略图同策略)。
4. T0.3 懒取协议改动触及 M2 已收口的列表契约(thumbnail 字段变 URL),
   需要前端同步改造——作为 M3 第一波,改完跑全量回归。
