# OCard PRD（v2 草案，待确认）

日期：2026-08-24（同日修订：需求变更为跨 Windows/macOS/Linux，技术栈由 Swift 原生改为 Tauri）
定位：复刻 KOCARD App 核心功能的**内部** DIT 素材备份管理工具，落实《摄影前后期技术规格和数据管理流程规范 OB/GF 001—2026（第2版）》（下称「规范」）。

## 1. 一句话定义

跑在 DIT 工作站上的跨平台桌面应用（Windows/macOS/Linux）：插卡 → 按规范自动建夹拷卡（HASH 校验、多目的地）→ 预览分类选片 → 转码/代理 → 交付打包，全程留痕，素材不出内网。

## 2. 已确认的范围决策

| 决策点 | 结论 |
|---|---|
| 产品形态 | 跨平台桌面应用（Windows 10+ / macOS 13+ / 主流 Linux），DIT 工作站使用 |
| AI 功能 | 只做本地选片辅助（去重聚类、质量评分、人脸检测）；**闭眼检测已砍**（2026-08-24 M3 决策门，见 §5.5）；**不做** AI 修图，修图归调色师 |
| 交付环节 | 自动打包 + 生成交付清单；上传百度网盘、发分享链接**人工**完成 |
| 手机素材 | 不纳入，只管相机/无人机/运动相机存储卡 |
| 技术栈 | Tauri 2（Rust 核心 + Web UI），打包 msi / dmg / AppImage |

## 3. 非目标（明确不做）

- AI 修图 / 文字指令编辑（KOCARD 原版功能，砍）
- 云盘 API（Google Drive/Dropbox/OneDrive/百度网盘自动上传）
- 手机相册同步、iOS 端
- 任何硬件（KOCARD GO 由读卡器 + 内网 NAS 替代）
- 视频剪辑本身（只管素材和代理，剪辑归剪辑师的 NLE）
- 多租户/权限系统（内部工具，操作人以登记名区分，不做账号密码）

## 4. KOCARD 功能 → OCard 映射

| KOCARD 功能 | OCard 对应 |
|---|---|
| 直连备份（免电脑拷 SSD） | 拷卡引擎：读卡器卷 → NAS/本地/移动硬盘，多目的地一次完成 |
| HASH 校验、断点续传 | 同等实现（见 §5.3） |
| 智能转码（HEVC 10-bit、三档压缩） | 转码引擎：ffmpeg 按平台调硬件编码，代理/归档两用（见 §5.6） |
| AI 智能选片（去重、荐优） | 本地 ONNX 模型实现，素材不出内网（见 §5.5） |
| 素材管理（口袋数据中心） | 项目管理 + 素材浏览 + 分类工作台（见 §5.2、§5.4） |
| 多路径传输（本地/NAS/云盘） | 本地/移动硬盘/NAS（SMB 挂载卷）；云盘砍 |
| 相册同步 | 砍（决策见 §2） |
| AI 修图 / AI Film / API 开放 | 砍 |

## 5. 功能需求

### 5.1 设备与存储卡登记

- 登记相机：型号、机位（A–Z）、使用者代称，自动生成规范编码（如 `DJIRonin4D_B_ZS`）。
- 登记存储卡并与相机关联（一卡一机），支持打印/显示辨识标签内容。
- 登记表全项目共享（存 NAS，见 §6.3），拷卡时自动带出编码用于命名。

### 5.2 项目管理

- 新建项目向导：选日期 + 项目名 → 生成 `YYYYMMDD_项目名` 项目文件夹于 NAS。
- 选工况：
  - **工况 A（视频剪辑）**：`1. 工程文件 / 2. 原始素材 / 3. 特别素材 / 4. 转码素材 / 5. 文字素材 / 6. 成片`。
    规范原文表1的序号有冲突（「文字素材」与「转码素材」都编 4、缺 5），本 PRD 按上述顺序取齐（**2026-08-24 已确认**）。
  - **工况 B（纯拍照）**：`1. 待分类 / 2..n 各分类（建项目时或过程中自定义）/ n+1. 精选（内含 待修、已修）/ n+2. 其他`。
- 项目列表页显示各项目状态：已拷卡张数/容量、分类进度、备份状态、交付状态。

### 5.3 拷卡引擎（核心）

- 自动检测插入的可移动卷；拷贝前双确认界面：选择该卡对应相机（自动带出编码）、填写内容备注（对应规范「摄影师和 DIT 两方确认」+「适当记录」）。
- 目标自动命名：
  - 工况 A：`2. 原始素材/YYYYMMDD_相机编码/`
  - 工况 B：`1. 待分类/时段_相机编码/`（时段如 `0101上午`，从素材时间戳自动推断，可改）
- **多目的地**：一次读源、并行写 N 个目标（NAS 主 + 本地/移动硬盘备），对应规范的全量备份责任。
- **HASH 校验**：默认 xxHash3-64（大文件快），拷完回读目标逐文件比对；结果写入 manifest（文件名、大小、hash、源卡、操作人、时间）。
- **断点续传**：任务中断后按 manifest 续拷，已校验文件跳过。
- 拷贝完成且校验 100% 通过后，提示「本卡可格式化」；**OCard 不代为格式化**（防误操作）。
- 速度实时显示；写 NAS 时按有线内网跑满为目标。

### 5.4 素材浏览与分类工作台（工况 B 为主）

- 网格预览 + 全屏对比，支持 JPEG/RAW/常见视频格式。RAW 走快慢双路径：优先提取文件内嵌的全尺寸 JPEG 预览（毫秒级、覆盖绝大多数机型），需要像素级查看时用 libraw 完整解码。
- 键盘驱动分类：数字键分到各分类夹、`P` 标精选（复制一份进 `精选/待修`）、`O` 进「其他」、`D` 标记删除。
- **删除永远两段式**：标记 → 汇总人工确认 → 移入项目内回收站（`.ocard/trash`，可恢复），不直接物理删除。
- 连拍组自动折叠显示（配合 §5.5 聚类），一组保留 1–2 张、其余批量处理。
- 「待修 → 已修」流转辅助：检测到已修文件夹出现成品时，提示删除待修中的对应原稿（人工确认）。

### 5.5 本地 AI 选片（无云端依赖，三平台一致）

- 推理统一走 **ONNX Runtime**（Rust 绑定），模型随应用分发，CPU 可跑、有 GPU 自动加速。
- **相似聚类/去重**：纯算法基线（拍摄时间邻近 + dHash 相似度)聚类连拍，每组按质量分推荐保留项（M3 决策门:embedding 模型砍——同等效果、零模型/许可证/打包风险；实测不够再议）。
- **质量评分**：清晰度（拉普拉斯方差，纯算法；人脸在场时按最大脸区域计）、曝光端部占比（纯算法）、人脸检测（YuNet ONNX，CPU 静态链接;GPU EP 顺延)。**闭眼判断已砍（2026-08-24 M3 决策门）**：无许可证干净且经真实样本验证的开闭眼模型；YuNet 5 关键点每眼仅 1 点，EAR 启发式不可实现——按本节诚实边界原则，宁可不做也不上不可信指标。
- **荐优**：按综合质量分排序、给「值得进精选」建议标记。
- **能力边界（诚实声明）**：本地算法对**客观指标**可靠——连拍去重、糊片、过曝/欠曝、人脸计数（合影中过小的人脸不判，只对达到最小像素尺寸的脸生效）；对**主观审美**（构图/角度「极好」）不可靠，本地美学模型效果平庸，荐优只按客观分排序，「精选」的审美判断仍归 DIT/摄影师。若将来想要接近 KOCARD 原版（Gemini 云端）的审美荐优，需破例接云端视觉 API，另行决策。
- AI 只排序和建议，**不自动删除、不自动挪动任何文件**；采纳与否由 DIT 决定。

### 5.6 转码引擎（工况 A 为主）

- 统一由 **ffmpeg sidecar** 承担，按平台探测可用硬件编码器：NVENC（NVIDIA）/ QSV（Intel）/ AMF（AMD）/ VideoToolbox（macOS）/ VAAPI（Linux），全部不可用时回落 x264/x265 软编。
- 代理转码：高负载素材（Log、高码率）批量转代理到 `4. 转码素材`，按相机分子夹。
- 归档转码：可选 HEVC 10-bit 三档压缩（高质量/平衡/高压缩），对齐 KOCARD；默认保留原文件。
- 拷卡时可勾选「拷完自动转代理」（对应规范中期工况 A 第 3 条）。

### 5.7 交付打包（工况 B）

- 选择已分类文件夹 → 按半天自动分包（依素材拍摄时间），包含精选与其他，**不压缩**，生成包文件夹 + 交付清单（每包内容、张数、容量）。
- 打包完成给出待上传列表，人工上传百度网盘、人工发链接；OCard 记录交付状态（已打包/已上传可手动勾）。

### 5.8 成片命名校验（工况 A，轻量）

- 监视 `6. 成片`，校验命名是否符合 `时间日期_片名_分辨率_用途_版本`，不符合的标黄提示；识别预览版（720p）与成品（4K）。

### 5.9 UI 风格基线（2026-08-24 增补）

- **严格复刻 OpenAI Codex 网页版的视觉语言**：近黑/近白双主题、克制的灰阶层次、大留白、细分割线、小圆角、无装饰阴影、低饱和单一强调色、克制的动效；正文无衬线字体，路径/哈希/相机编码等技术信息用等宽字体点缀。
- 复刻的是版式与视觉语言，**不使用** OpenAI 的商标、名称、图标等品牌资产。
- 实现时以 Codex 网页版截图逐项对照校准（配色取色、间距、字号层级），作为 M1 起所有界面的验收基准之一。

### 5.10 审计日志

- 拷卡、校验、删除确认、打包等关键操作追加写入项目内日志（操作人 = 当前登记的 DIT、时间、动作、对象），支撑「双岗互相监督」。

## 6. 架构设计

### 6.1 分层

```
OCard (Tauri 2)
├── UI 层（Web，React + 虚拟化网格）：项目列表 / 拷卡任务 / 分类工作台 / 转码队列 / 交付打包 / 设置登记
├── Rust 核心（tauri commands + 后台任务，进度经事件推送 UI）
│   ├── copy_engine    拷贝+校验+续传（单读多写，流式）
│   ├── hash           xxHash3-64 流式计算
│   ├── project_store  项目模板/命名规则/状态（规范的代码化）
│   ├── media_indexer  缩略图/EXIF/拍摄时间提取（缓存于 .ocard/）
│   ├── culling        聚类/评分(纯算法)+人脸(ONNX)(后台作业)
│   ├── transcode      ffmpeg sidecar 队列（按平台选硬件编码器）
│   ├── packaging      半天分包+清单
│   └── audit_log      追加式操作日志
└── 存储：一切项目级状态放 NAS 项目夹内 `.ocard/`（JSON/SQLite + 缩略图缓存）
```

### 6.2 关键数据流（拷卡）

插卡检测 → 选相机编码+备注 → 目标路径按规范生成 → 流式读源（边读边算 hash）→ 并行写多目的地 → 回读校验 → manifest 落盘 → 日志 → 提示可格式化。

### 6.3 多工作站协同（多设备操作）

规范要求 DIT 一主一副，两台（或更多）工作站可以混装 Win/macOS/Linux。**无服务端**，NAS 项目夹本身就是「数据库」：

- **接入方式**：每台工作站在 OCard 里配置自己的 NAS 根路径（macOS/Linux 挂载点、Windows 盘符或 UNC），打开同一个项目文件夹即完成「加入」。项目状态内只存相对路径，因此各机路径形式不同不影响互通。
- **写入模型（免锁）**：SMB 上跨平台文件锁不可靠，故不用锁。每台工作站只追加写**自己的**日志文件 `.ocard/journal-<机器ID>.jsonl`（登记、拷卡记录、分类动作、审计事件都是一条条追加的事件），永不写别机的文件——从根上消灭并发写冲突。
- **读取模型**：打开/刷新项目时合并所有 `journal-*.jsonl`，按时间戳重放事件得到当前状态（登记表、拷卡清单、分类进度）。SMB 没有可靠的变更通知，采用定时轮询（约 5–10 秒）拉取别机新事件。
- **并行拷卡**：两台机同时拷**不同的卡**是主场景，各自的目标文件夹（`日期_相机编码` / `时段_相机编码`）天然互不相交，完全并行。OCard 界面上能看到对方正在拷哪张卡（来自事件流），避免重复拷同一张卡。
- **罕见冲突**：若两人对同一张照片做了不同分类，按事件时间戳后写胜，两次操作都在审计日志留痕（这本身就是「双岗互相监督」的实现）。
- **离线/断连**：NAS 断连时拷卡任务挂起、事件先落本地暂存，恢复后续传并补写事件；不产生半截状态。
- **机器 ID 与操作人**：机器 ID 首次启动生成并持久化；操作人取当前登记的 DIT 名，事件同时带机器 ID + 操作人。

### 6.4 错误处理原则

- 拷贝/校验失败：逐文件标红、可单独重试，任务不整体作废。
- NAS 断连：任务挂起可续传，不产生半个文件（临时名写入、校验后改名）。
- 一切破坏性动作（删除、覆盖）人工二次确认；格式化不代做。
- **零静默 fail-open（2026-08-24 用户确认的硬性 UX 原则）**：任何降级/跳过/兜底路径必须同时向用户发出可见的 warning/error（`app://notice` 通道 → 前端通知中心），只写日志不算提示。评审把「是否存在无提示的 fail-open」列为标准检查项。

### 6.5 平台适配要点

- **可移动卷检测**：Windows 用 Win32 卷通知、macOS 用 DiskArbitration、Linux 用 udev；统一抽象为 Rust 层「卷事件」接口，兜底方案为轮询挂载表。
- **NAS 路径**：同时支持挂载点路径（macOS/Linux）与盘符/UNC 路径（Windows）；项目状态内只存相对路径，NAS 根路径按工作站各自配置。
- **文件名边界**：素材/文件夹命名统一过滤 Windows 非法字符，保证三平台互通。
- **Webview 来源（不自带 Chromium）**：Windows 用系统 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK。Linux **不需要自己嵌浏览器内核**：deb/rpm 形态声明 `webkit2gtk-4.1` 为系统依赖，AppImage 形态由打包器自动把 WebKitGTK 及其依赖库打进包内（包体约 70–100MB，换来目标机零依赖）。代价：WebKitGTK 渲染兼容性略逊 Chromium，个别发行版/NVIDIA 环境需 `WEBKIT_DISABLE_DMABUF_RENDERER=1` 兜底，UI 避免使用 Chromium 专属特性。
- **分发**：Windows msi/nsis、macOS dmg（签名可后置）、Linux AppImage/deb/rpm；ffmpeg 与 ONNX 模型随包分发。

## 7. 里程碑（SDD）

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M1 拷卡底座** | 项目管理+建夹模板、设备登记、拷卡引擎（HASH/多目的地/断点续传）、审计日志 | 真卡实拷：一张卡一次操作进 NAS+备份盘，校验 100%，中断可续，命名全符合规范 |
| **M2 分类交付** | 缩略图索引、分类工作台（键盘流）、回收站、交付打包+清单 | 千张级素材完成工况 B 全流程：分类→精选→打包，全程不出 OCard |
| **M3 智能与转码** | AI 选片（聚类/评分/人脸/荐优；闭眼已砍见 §5.5）、转码引擎（代理+归档）、成片命名校验 | 千张连拍聚类+评分 ≤5 分钟；Log 素材批量转代理入 `4. 转码素材` |

每个里程碑按既定评审流程：实现评审 opus-4.8 + gpt-5.6-sol（max）并行；里程碑终审 gpt-5.6-sol（max）+ fable-5 双报告收敛。

## 8. 测试策略

- 单元：命名规则、建夹模板、manifest、半天分包逻辑（Rust 侧，三平台 CI 全跑）。
- 集成：用磁盘映像模拟存储卡，全流程拷贝+故意损坏文件验证校验拦截、断点续传。
- 平台矩阵：拷卡/校验/续传、卷检测、NAS 路径三平台各验一遍；主力实测在 macOS + Windows，Linux 以 CI 与抽测为主。
- 性能基准：10GB 混合素材拷卡吞吐（目标：跑满 2.5Gbps 内网 ≈ 280MB/s）；千张聚类耗时。
- UI 冒烟：分类工作台键盘流。

## 9. 成功标准

一场真实活动（工况 B）从插卡到交付打包全程在 OCard 内完成，除「上传百度网盘」外无人工文件操作；HASH 校验覆盖率 100%；两名 DIT 在各自工作站可见同一项目状态。

## 10. 仓库与 CI/CD

- 代码托管：GitHub **公开**仓库 `hanbin2007/OCard`（用户要求 public；PRD 与规范流程描述随仓库公开，不含个人信息）。
- CI（push/PR 触发）：lint（cargo fmt / clippy -D warnings、tsc + vite build）→ cargo test → **三平台完整 Tauri 打包**（ubuntu / macos / windows），产物上传 Actions Artifacts——每次提交都验证云端三平台可构建。
- CD：推 `v*` 标签自动三平台构建并创建 GitHub Release 草稿，附 msi/nsis、dmg/app、AppImage/deb/rpm 安装包。
- 包管理：pnpm（`packageManager` 锁定版本；pnpm 11+ 的依赖构建脚本经 `pnpm-workspace.yaml` 的 `allowBuilds` 显式放行）。
- 代码签名：**macOS 做**——用户持有付费 Apple Developer 账号（Team `NCLY9ZGRMZ`），Release 工作流经 tauri-action 自动签名 + 公证，证书等 6 项存 GitHub Secrets（配置步骤见 `docs/signing-setup.md`）；Windows 暂不签（SmartScreen 点一次即可）。
