# 滚动条不同步:四轮误诊与收敛(2026-08-27 / 28)

> **第四轮才是真因。前三轮(含本文档原先标题里的「最终收敛」)全部没解决用户报障。**
> 下方 §「第三轮」及之前的内容保留原样,作为误诊过程的记录;真因见文末第四轮。

用户症状:除项目管理页外,所有可滚屏幕「滚动和滚动条不同步」。
本记录同时留下**误诊过程**,因为它比结论更值钱——同一个坑掉进去三次。

## 三轮排查

| 轮次 | 假设 | 动作 | 结果 |
| --- | --- | --- | --- |
| 1 | 自定义 `::-webkit-scrollbar` 把滚动容器踢出 WebKit 合成器异步滚动 | 删伪元素,改标准 `scrollbar-width` | 没修好 |
| 2 | 滚动容器 `.content` 自身的 transform 过渡动画同上 | 动画挪到 `.content__inner`(af39168) | 没修好 |
| 3 | **嵌套滚动容器** | 见下 | 待用户复测 |

前两轮共同的错误:**在渲染引擎方向做自洽的机制推理,却没有任何测量**。两条改动本身都独立正确(值得保留),但都不是病因;它们的代码注释此前把「这就是病因」写成事实,是把后来者(和第三轮的自己)推进同一个坑的直接原因——本次已全部改写为「独立正确,但不是那次症状的病因」。

## 定向的两个问题

真正把方向掰正的是向用户提的两个判别性问题,而不是继续读代码:

- **「停下来也错位」** → 排除合成器/主线程相位差(那类问题松手必然收敛对齐)
- **「拖动滚动条本身也错位」** → 指向「条与内容分属不同容器」

结论:是布局层问题,与渲染引擎无关。**布局问题在 Chrome 里同样现形**,于是起 vite dev server 用浏览器直接量几何——一量就露馅,不到十分钟。

## 真因

一屏之内存在两个滚动容器:

- 拷卡屏:`.content`(可滚 198px)内嵌 `.files__scroll`(`max-height:420px; overflow-y:auto`,自滚 88px)
- 选片屏:`.content` 内嵌自滚的虚拟网格 `.sorting__grid`
- 项目管理页:`.welcome-sub__body`(auto)与屏内 `.content`(auto)两根条几乎重叠在同一条右缘——**这才是「拖条也错位」最贴切的现场**

鼠标落点决定滚哪一层,而用户盯的是主区右缘那根条。内层滚时它纹丝不动,内层到底后才突然接管。

## 不变式(修法的准绳)

评审(opus P1-3)纠正了第一版规矩的写法。最终口径:

> **同一片区域、同一时刻,只有一个容器会响应滚轮 / 出条。**

不是「结构上只许有一个 `overflow:auto`」——后者会逼出更坏的结果:一旦布局退化就宁可把内容裁掉(见 P0-1)。一个 `scrollHeight === clientHeight` 的兜底 auto 容器对用户不存在,却能在退化态兜住可达性。

## 双路评审(codex gpt-5.6-sol max + opus)结论与处置

codex `REQUEST_CHANGES`(P1×4);opus 报 **P0×2**(带 headless Chrome 实测数值)。两份高度互补,全部处置:

| 项 | 处置 |
| --- | --- |
| **P0-1**(opus)`.content--flush{overflow:hidden}` 在横幅堆叠时把内容裁成不可达,VirtualGrid 视口塌成 0 后静默退化为按 6 行渲染——**我自己造出了 fail-open** | 改兜底 `overflow-y:auto` + `.sorting__grid-wrap{min-height:160px}`。实测:日常态外层 `scrollHeight==clientHeight`(不出条、不吃滚轮),退化态可滚、网格保底 180px |
| **P0-2**(opus)/ P1-1(codex)`.files__scroll` 展开后 sticky 表头彻底失效(`overflow:hidden` 的祖先 `.list` 建立了 scrollport) | `.list--files{overflow:clip}`(`@supports` 包裹,老内核回退)。**第一版选择器写反了**(以为 `.list` 在 `.files__scroll` 内,实际是祖先),浏览器实测才发现;修正后实测表头 `top=0` 精确吸在 `.content` 顶边 |
| P1-1(opus)「加载更多」被自己推到几千像素外,统计头随之滚走 | 触底自动续拉(IntersectionObserver + `rootMargin:200px`),复用选片屏 `onEndReached` 范式;按钮保留为手动出口。注:DOM 总量本就与改前相同(旧的 420px 只是裁剪),真正的代价是导航距离 |
| P1-2(opus)af39168 的「全部屏幕都有 content__inner,无遗漏」不成立 | 选片屏确实没有,该屏自 af39168 起就没有进场动画、`--flush .content__inner` 是死规则。补上包裹层——**并因此引出高度链断裂**:`.sorting{height:100%}` 失去参照被撑到 3494px,外层日常态可滚 2876px(嵌套又回来了),补 `height:100%;min-height:0` 修复,实测三层 825=825=825 |
| P1-4(opus)`welcome.css` 不在样式守卫扫描内 | `tokens.test.ts` 的 `STYLESHEETS` 补 `welcome`;随即红出两条违规并修:`transition: background-color`→`background`;非浮层 `box-shadow` 改 `outline`(全仓唯一一处违反「阴影只给浮层」) |
| P1-5(opus)/ P1-4(codex)零布局回归测试 | jsdom 无布局,必然假绿 → 进 E2E(`smoke.e2e.mjs`):每屏断言①正文区至多一个**真的能滚**的容器;②不存在「能滚却被 hidden 裁掉」的容器(零静默) |
| P2 批 | 步骤序号 a11y(勾号 `aria-hidden` 后补 `sr-only` 序号 + `role="list"`);副行改「文件夹名 · 工况」且只有文件夹名用 mono(窄宽先截冗余标签而非有用信息);`--text-quaternary` 不存在→ tertiary;`.topbar__back` 多余 margin;reduced-motion 注释与事实对齐;`.welcome-recent__folder` 两条冲突 `display` 清理 |

## 声明边界

- **本次只是「浏览器实测嵌套已消除」,不等于「用户症状已消失」**——这正是前两轮的教训。结论待用户在 macOS 实机复测。
- 前两轮改动不回滚:各自独立正确,是合理的风险隔离,只是与本症状无因果。
- `NewProjectWizard` / `SortingScreen` 新增包裹层后 JSX 缩进未重排(仓库无 JS formatter,重排本身是巨大 diff),记为技术债。
- E2E 只在 Linux tauri-driver 上跑,macOS WKWebView 的原始症状仍需目标机验收。

# 第四轮:真因(2026-08-28,commit 865efe0)

前三轮全部没解决用户报障。用户第四次反馈只有五个字:「一点都没变化」,随后一句话点破:

> 「你的左半边和右半边都能滚,而在窗口不够大的时候会隐藏右边,甚至会叠到本来的左半边上面」

## 真因

四处「双列 grid + 侧栏 `position: sticky`」布局(`.copy__form` / `.devices__form` /
`.wizard__preview` / `.detail`),在窗口变窄、布局塌成**单列**后没有取消 sticky。

关键机制(两位评审各自独立实测,WKWebView 与 Chrome 行为一致,**不是 WebKit 独有**):
单列下 sticky 侧栏的约束矩形是 grid **容器**而非它自己那一格,所以它能在整屏行程里
粘住不动,后面的内容从身下滚过 —— 内容视觉上不动、滑块照走,停下来对不上,拖条也对不上。

实机取证(Safari 同引擎 + 临时诊断层,已删):

```
1200 宽 · 修复前:copy__form pos=sticky  formTop=66     滚 148px,表单纹丝不动
1200 宽 · 修复后:copy__form pos=static  formTop=-1329  内容位移 148 == scrollTop 变化 148(1:1)
```

## 为什么前三轮找不到

1. **判别式找错了方向**:「停下来也错位」被我解读成「布局/滚动范围算错」,方向对,
   但我盯的是「哪个容器在滚」,而病灶根本不改变任何容器的 `scrollHeight/overflow`。
2. **测量窗口宽度不对**:我在 Chrome 里量几何用的是 1556 宽窗口,`.copy` 的断点是
   1312 → **根本没触发单列**,量出来的数字全是正常的。用户窗口 1280,正好落在断点内侧。
3. **「唯独项目页正常」这条线索把我带偏了**,而且我给出的解释是错的 ——
   见下方「被评审推翻的解释」。

## 被评审推翻的解释(重要)

commit 865efe0 原本写:「项目屏断点 1080,用户 1280 窗口仍是双列,所以正常」。
**这是错的**(opus 实测推翻):`ProjectsScreen` 只在欢迎窗口渲染,而欢迎窗口
`920×600 / minWidth 820` → 永远 ≤1080 → 它当时**同样是单列 + sticky**。

真正的判别式是 **DOM 顺序,不是断点**:

- `.copy__form` / `.devices__form` 是堆叠后的**首个**子元素 → 钉在顶端,后面一大坨从身下滚过 → 症状剧烈
- `.detail` / `.wizard__preview` 是**最后一个** → sticky 没有行程 → 看着正常

留着「断点」这条错误因果,下一个人会去调断点而不是看 DOM 顺序。**四处一律取消,不依赖这个区分。**

## 修法(采纳评审建议的根本形态)

第一版修复用 `@media (max-width) { position: static }` 打补丁,并且**栽了第二跤**:
覆盖写在基础规则之前,媒体查询不提升特指度、被后面的 sticky 盖掉,等于没写
(诊断层直接照出 `pos=sticky` 没变)。

最终改为 **mobile-first**:基础形态 = 单列 + 静态定位,「双列」与「侧栏吸顶」焊进
**同一条** `@media (min-width: …)`。结构上不可能再漂移,且降级方向安全 ——
任何一条查询失效都只退回单列,不会退回病态。

## 防复发

`src/styles/sticky.test.ts` 重写(上一版被评审用变异测出**四类假绿**):
剥注释(用等量空白填回以保住下标)、glob 全量扫 `src/styles/*.css`、逐规则块解析
(能看见缩进的/后代的/逗号列表里的每一个选择器)、断言「sticky 只许出现在 min-width 查询内」
+「双列与吸顶在同一块里」+「基础形态是单列」+「解析器自身有产出」。

变异验证(全部能红):裸露 sticky、断点漂移、`max-width` 里新增 sticky、
**把真规则整段换成同内容的注释伪代码**、文件末尾追加裸 sticky。

E2E 补几何断言:1200 宽下滚 148px,受管侧栏必须同步位移 148 —— 这条病灶不改变
任何容器的 overflow,原有的「至多一个活跃滚动容器」不变式完全覆盖不到它。

## 顺带修掉

- 回收站窄宽(1100–1180,主窗口可达)藏错了列:藏掉**文件名**却留着原路径,
  且 4 个可见元素挤进 3 条轨道 → 「恢复」按钮换行。轨道数必须等于可见元素数。
- 三处仍把「嵌套滚动」写成本症状真因的注释已纠正为「独立存在的真问题,但不是那个症状的病因」。

## 未收口(诚实记录,codex 明确指出不应宣称「全局收口」)

1. **`.content--flush` 退化态仍可能双滚动**:横幅(筛选提示/待修清理/缩略图降级/
   交付锁/索引)全部叠加、连 160px 保底网格都放不下时,外层兜底 auto 与自滚的
   `.sorting__grid` 会同时有溢出。不能退回 `overflow:hidden`(那是零静默违规)。
   正解是让 VirtualGrid 用外层单一滚动根,或把横幅纳入同一滚动面 + 横幅数量本身有界。
2. **文件明细无虚拟化**:取消内滚后首批 200 行全展开、触底续拉持续扩张 DOM,
   且进度刷新每 ~2s 序列化全部已加载行,几千素材时页面/DOM/IPC 成本无上限。
   正解是基于外层滚动根的虚拟列表。
3. **`.wizard` 的 1312 断点用错上下文**:向导在 920 宽的欢迎窗口里、外层 `.npw`
   恒为 860px,该断点表达不了任何真实约束,应改容器查询或按 welcome 内容宽度定。
4. **`scrollbar-width: thin` 只写在 `:root`**:该属性不继承,真正滚动的是 `.content`
   等内部容器,Windows/Linux 上仍是默认粗细。要么显式列出滚动容器,要么去掉「细」的承诺。
5. `.dialog` 仍是「自己滚 + 自身被 transform 动画」的同型结构;`.group-overlay__grid`
   在 `.dialog` 内构成嵌套滚动(浮层不在 E2E 扫描根内)。
6. **本轮只有 `.copy__form` 有实机测量**,其余三处按同构推断修复;Sorting/Transcode/Trash
   不受本 commit 影响。**用户实机复测仍是唯一的验收标准。**
